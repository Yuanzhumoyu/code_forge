# 生成物编译画像（V7 度量：分段体积 + 编译时间归属）

> 采集日期 **2026-09-24**，本机（Windows x86_64，`nightly-2026-09-05`）。
> 目的 = 计划 §5 **V7**「语义层表化」的判据：x86 的 lowering 段（下称 **C 段**）是否仍是
> 编译时间主因，表化的净收益是否 ≥15% token **且**不增编译时间。
> **结论：不做表化**（理由与触发条件见文末），本节留下可复现的数字与口径。

## 1. 口径与命令

- **体积**：`expand_file(...)` 产出的 token 文本字节数（= build script 落盘件正文，
  v18 S10d 的紧凑打印）。分段按生成器发射的顶层项边界切分，脚本 `target/v7_sections.py`
  （跑完即删，逻辑见本文「段定义」）；dump 脚本 `target/v7_dump`（临时集成测试，跑完即删）。
- **编译时间**：独立 probe crate（`target/v7_probe/`，`[workspace]` 与主工作区隔离，
  依赖 `forge-isa-runtime` + `smallvec`，`src/lib.rs` 只写 `include!("<生成物变体>.rs")`），
  `CARGO_INCREMENTAL=0 CARGO_TARGET_DIR=target/v7_probe_target cargo check --offline`，
  **取 3 次最小值**；变体间只差生成物文本，flags 完全一致 ⇒ 相对差有效。
  脚本 `target/v7_measure.py`（跑完即删）。
- **变体**（文本级、语法合法，用花括号配对定位，跳过字符串/raw 字符串）：
  `full`（原样）、`no_lower_body`（`lower_inst` 的**函数体**换成 `unimplemented!()`）、
  `no_spec_tests`（`__spec_tests` 的模块体换成空）、`no_both`。
- **别把 probe 的数字当成整 crate 的数字**：probe 是"单个生成物模块 + 元数据"的全量重检；
  真实 `cargo check -p forge-codegen` 走增量编译，改一个谱只有 9.05 s（见 §4）。

段定义（按出现顺序切分，标记即生成器发射的顶层项）：

对照 V0 基线（2026-09-23，`docs/plans/forge-isa-dsl-v19-plan.md` §10.1）：x86 全件
1,336,624 → **1,554,299**（+16%）——增长全在 `spec_tests`（V3 向量 138 条 + V3d 派生枚举器
602 条），`no_tests` 件只从 1,009,125 → 1,015,134（+0.6%）。

## 3. 编译时间归属（probe crate，全量重检）

| ISA | full | 去 C 段函数体 | C 段占比 | 去 spec_tests 模块体 | spec_tests 占比 | 去两者 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| x86 | **49.70 s** | 6.40 s | **43.30 s（87.1%）** | 37.56 s | 12.13 s（24.4%） | 5.80 s |
| riscv64 | 6.46 s | 3.00 s | 3.46 s（53.5%） | 4.50 s | 1.96 s（30.3%） | 2.64 s |
| arm64 | 3.35 s | 2.71 s | 0.64 s（19.0%） | 2.50 s | 0.85 s（25.3%） | 2.17 s |

三点读数：

1. **C 段是生成物编译时间的主因（x86 87%）**——这**修正**了 V0 时期"冷启动由 rustc 解析
   1.3 MB 生成物主导"的粗判断：解析只占零头，真正贵的是 lowering 段那 197 条规则的
   **类型检查/借用检查**（`if let Inst::X { … }` 链 + 每规则各自的发射序列）。
2. **代价超线性**：C 段每 KB 的检查时间 x86 0.137 s/KB、riscv64 0.018 s/KB、
   arm64 0.029 s/KB——x86 是 riscv 的 7 倍以上（规则更多、每条序列更长、`{cc}`/谓词/临时寄存器
   更复杂）。
3. `spec_tests` 段虽然比 C 段更大（x86 538 KB vs 315 KB），只占 24%——因为它在**非 test
   构建里被 `cfg(test)` 排除**（只解析、不检查）。（跑 `cargo test` 时它才是真成本。）

## 4. 真实 crate 的增量路径（为什么日常不受 87% 影响）

| 场景 | 耗时 |
| --- | ---: |
| `cargo check -p forge-codegen`（首次，含依赖检查） | 106.87 s |
| 紧随其后、改 `isa/x86_v12.toml` 的 mtime（build script 重跑、生成物**内容不变**） | **9.05 s** |

⇒ 日常改谱走**增量**：rustc 按文件内容指纹跳过重检，只有 build script 重跑 + 元数据校验
（9 s）。**87% 那个数字只在"生成物内容真的变了"或冷构建（CI、新机、`cargo clean`）时才兑现**。

## 5. 表化的收益估算（V7 判据的两个口径）

- **数据下限**：x86 的 `[[lowering]]` 规则在 TOML 里合计 **42,729 B**（其中 `insts` 数组
  18,828 B）——任何表示形式都至少要存这些；而生成物里的 C 段是 **315,255 B**（≈7.4×）。
- **net 估算**（把 197 条规则的发射序列换成"数据表 + 通用解释器"）：
  数据表（含操作数映射/谓词/临时寄存器等 Rust 侧已有信息）实测口径下乐观 40 KB、悲观
  120 KB；解释器 10–25 KB（手写在运行时/generator 里，只发射一次）。
  ⇒ **净省 170–265 KB**：
  - 对**全件**（1,554 KB）：**11.0% – 17.1%**；
  - 对**不含 spec_tests 件**（1,015 KB）：**16.8% – 26.1%**。
- 编译时间侧（若解释器足够通用）：x86 的 C 段 43.3 s 里很大一部分会消失，全量重检
  预期从 49.7 s 降到 ~10–15 s 量级（**未实测**——本轮没有实现解释器）。

## 6. 与既有 S8b-2 度量的关系（口径要对齐）

S8 时代已经量过同一件事，结论也是"不做"，但**口径不同**（见
`docs/performance/bench_baseline.md` 的「S8b 立项度量」与「S8b-2」段）：

| 口径 | 收益 | 出处 |
| --- | --- | --- |
| 只表化**均匀发射体**（`Inst` 构造里只有占位与字段名）：x86 70 条 / 21.9 KB | 净回收 **x86 1.2% / riscv 2.5% / arm64 0.9%** | S8b-2a（2026-09-21） |
| **全体表化**（含复杂体）：上限 221 KB（x86，全部件的 21.9%）——**未扣**解释器与数据表成本 | 上限 21.9% | S8b-2 |
| 本次 V7：全体表化并**扣掉**数据表（40–120 KB）+ 解释器（10–25 KB） | 全件 **11.0%–17.1%**；不含 spec_tests 件 16.8%–26.1% | 本文 §5 |

S8b-2a 之所以只有 1.2%，是因为**均匀体只占发射体的 9%**；V7 的 11–17% 是"连复杂体一起换掉"
的乐观区间，落在 S8b-2 的 21.9% 上限之下——三者不矛盾：**真正的成本项是那 215 条异质发射体
（x86 平均 1,030 B/条），要变成数据就必须写通用解释器**。

V7 相对 S8 的**新增事实**只有一条，但很关键：**C 段确实是生成物编译时间的主因（x86 87%）**。
S8 时代的 A/B 结论是"生成物文本 −7.5% 在 `cargo check` 上测不出差别"（基准噪声内），
而 V7 用"把 C 段函数体换成 `unimplemented!()`"这种**大颗粒**对照，第一次证明了这块的
**typecheck 成本**量级——它不推翻 S8 的结论（token 侧不够），但给出了将来重启的判据（§6 触发条件）。

## 7. 结论：**不做表化**（默认不做，给触发条件）

判据是"**净收益 ≥15% token 且不增编译时间**"：

- 15% 这条：**在"全件"口径下未过**（乐观 17.1% / 悲观 11.0%，中位 ~14%），只在
  "不含 spec_tests"口径下明显过线；而 published 口径一直是全件（V0 §10.1 的表就是全件）。
- 编译时间这条：会**大降**，但它降的是"生成物内容真的变了"与冷构建；日常增量路径
  （9.05 s）不受影响。
- 代价：要写**通用解释器**并迁移 197+106+19 条规则的全部表达力（占位符/临时寄存器/reloc/
  `{cc}`/内存风味/宽度提示/多态 `ref`），失败模式是"生成的机器码悄悄变了"——探针
  （`isa_roundtrip_guard` 的 602/327/332 条 + 361 条向量 + 黄金字节）能兜住，但这一轮的工作量
  与风险远大于它换来的 token 收益。⇒ 与 S8b-2 的判断一致。

**将来重启 V7 的触发条件**（任一满足就该做 prototype，而不是现在做）：

1. 冷构建成为真实痛点：CI 冷检查/新机首次 `cargo check` 超过约定的预算（当前本机 free 106.87 s，
   其中生成物部分 ~50 s）；
2. 出现"要按 op 细分 lowering 生成"的需求（如按扩展分包：RV64A/V、AVX-512 分开生成），
   那时天然需要数据化；
3. 全件 net 收益被新的度量推翻（例如新 ISA 的 C 段占比 ≥35%）。

**若只想压冷构建时间，先试成本低得多的中间方案**（都无需解释器）：

- **规则体去重**：把重复的发射结构（内存风味、VEX/EVEX 形态、`{cc}` 分派）抽成共享 helper，
  直接减少被 typecheck 的函数体字节数——与 token 收益无关，但正对 §3 的瓶颈；
- **`parts` 粒度**：宿主只要编解码时别生成 `tm`（V1 已有的能力，实测 x86 `no tm` 件
  576 KB vs 全件 1,015 KB）；
- **spec_tests 只在 test 构建里展开**：它 34.6% 的体积与 24% 的解析时间是白付的（虽然
  非 test 构建不检查）；若要进一步省，可给它加一层"按需部件"。
